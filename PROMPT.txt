# NEXO --- ESPECIFICAÇÃO MESTRE DO PROJETO

Versão: 1.0 Status: base oficial para desenvolvimento Produto: NEXO
Idioma principal: Português (Brasil) Objetivo: plataforma gratuita e
gamificada de preparação para o ENEM, com IA para personalização do
estudo.

------------------------------------------------------------------------

# 1. VISÃO DO PRODUTO

O NEXO não deve ser tratado como um simples site de questões ou como um
chatbot.

O NEXO é uma plataforma de estudo integrada.

Princípio central:

> A plataforma identifica o que o estudante precisa aprender, ensina,
> pratica, avalia e decide qual deve ser o próximo passo.

Tudo relacionado ao estudo será gratuito.

A única área de monetização será a personalização do avatar.

Monetização: - skins - roupas - chapéus - acessórios - efeitos -
molduras - fundos - itens cosméticos - pacotes cosméticos - NEXO Coins

Não vender: - respostas - questões - conteúdo - correção de redação -
mapas mentais - desempenho - plano de estudos - vantagem acadêmica

------------------------------------------------------------------------

# 2. IDENTIDADE

Nome: NEXO

Conceito: Conexão entre estudante, conhecimento e evolução.

Posicionamento: Uma plataforma moderna, inteligente, gratuita e
gamificada para preparação para o ENEM.

Possíveis frases de marca: - Seu caminho até o ENEM. - Estude. Evolua.
Conquiste. - Conecte-se ao seu próximo nível.

A frase principal pode ser definida posteriormente.

------------------------------------------------------------------------

# 3. LOGO

Manter a logo já aprovada.

Símbolo: - livro aberto - seta apontando para evolução - capelo de
formatura

A logo deve transmitir: - educação - evolução - conquista - tecnologia

Criar versões: - logo completa - símbolo isolado - versão horizontal -
versão para favicon - versão monocromática clara - versão monocromática
escura

Os arquivos devem ficar em:

/public/brand/

------------------------------------------------------------------------

# 4. DIREÇÃO VISUAL

Estilo: Minimalista + tecnológico + gamificado.

O site NÃO deve parecer: - infantil - exageradamente gamer - cheio de
neon - cheio de gradientes - cheio de glassmorphism - poluído

Deve parecer: - premium - moderno - limpo - rápido - confiável -
tecnológico - agradável para estudar por muito tempo

Tema principal: Dark mode.

Paleta base:

Background: #0A0A0B

Surface: #111214

Card: #17181B

Border: #282A2E

Texto principal: #F5F5F5

Texto secundário: #9A9CA3

Azul de destaque: usar azul elétrico inspirado na logo.

Regra: Azul é cor de ação/destaque. Não pintar a interface inteira de
azul.

------------------------------------------------------------------------

# 5. TIPOGRAFIA

Fonte principal: Inter

Fonte alternativa: Manrope

Pesos: - 400: texto normal - 500: texto secundário/labels - 600: títulos
menores - 700: títulos principais e números importantes

Evitar fontes decorativas.

------------------------------------------------------------------------

# 6. ÍCONES

Usar SVG.

Biblioteca principal sugerida: Lucide React para ícones funcionais.

Ícones específicos da marca podem ser SVG próprios.

Criar:

/public/icons/ navigation/ subjects/ actions/ gamification/ avatar/
status/ achievements/

Preferir: - SVG - viewBox consistente - currentColor - tamanhos
padronizados - acessibilidade

Não colocar SVG gigante diretamente em componentes.

------------------------------------------------------------------------

# 7. ANIMAÇÕES

Biblioteca: Framer Motion.

Princípio: A animação deve ajudar a entender a interface.

Durações: - microinterações: 120--180 ms - transições: 180--250 ms -
animações especiais: 300--700 ms

Usar: - fade - pequeno translate - scale mínimo - progress bar -
skeleton - expansão de cards - transição de páginas - feedback de
acerto - ganho de XP - level up - conclusão de missão - abertura de
loja - equipar item - expansão de mapa mental

Evitar: - animação constante - elementos pulando sem motivo - excesso de
partículas - transições lentas

Implementar suporte a: prefers-reduced-motion

------------------------------------------------------------------------

# 8. TECNOLOGIA

## Frontend

Next.js com App Router TypeScript Tailwind CSS shadcn/ui Framer Motion
Lucide React React Hook Form Zod Zustand quando estado global realmente
for necessário Recharts para gráficos @xyflow/react para mapas mentais

## Backend

Usar inicialmente o próprio Next.js para: - Route Handlers - Server
Actions quando apropriado - lógica de servidor - integração com IA -
validações - operações protegidas

Não criar um backend separado no começo sem necessidade.

## Banco e infraestrutura

Supabase: - PostgreSQL - Auth - Storage - Realtime quando necessário -
Edge Functions quando fizer sentido

Supabase será o backend principal.

## Deploy

Frontend: Vercel ou plataforma equivalente compatível com Next.js.

Banco/Auth/Storage: Supabase.

------------------------------------------------------------------------

# 9. SUPABASE

Usar: - Supabase Auth - Supabase PostgreSQL - Supabase Storage - Row
Level Security (RLS)

Autenticação: - email/senha - recuperação de senha - eventualmente
Google OAuth

Perfil do estudante separado do auth.users.

Criar RLS desde o início.

Regra: Um estudante só pode acessar seus próprios dados, salvo dados
públicos/compartilhados explicitamente.

# 24. NEXO COINS

Moeda virtual.

Ganhos possíveis:

Questão respondida: +2

Questão acertada: +3

Missão: +20

Meta diária: +30

Simulado: +50

Sequência: bônus

Conquistas: bônus

Compra de Coins: permitida futuramente.

Implementar proteção contra duplicação/fraude.

O saldo nunca deve ser alterado diretamente pelo frontend.

Toda alteração deve passar pelo servidor e gerar registro de transação.

------------------------------------------------------------------------

# 25. LOJA E PAGAMENTOS

O pagamento real deve ser separado da moeda virtual.

Arquitetura:

Cliente → servidor → provedor de pagamento → webhook → servidor →
registro de compra → entrega das Coins/item

Nunca confiar no frontend para confirmar pagamento.

O provedor de pagamento pode ser escolhido posteriormente.

Para o Brasil, avaliar provedores como Mercado Pago ou Stripe.

Não implementar pagamentos antes de o sistema de inventário estar
estável.

# 29. IA --- ARQUITETURA

Criar um AI Gateway.

Nunca chamar o provedor diretamente de vários componentes.

Estrutura:

/lib/ai/ gateway.ts providers/ gemini.ts groq.ts openrouter.ts prompts/
schemas/ validators/

Interface conceitual:

generateQuestion() explainAnswer() generateStudyContent()
generateMindMap() generateEssayTopic() gradeEssay() recommendNextStudy()
generateSimulation()

O frontend chama o backend.

O backend chama o AI Gateway.

O AI Gateway escolhe o provedor.

------------------------------------------------------------------------

# 30. IA SEM API CARA

O projeto deve começar usando provedores com opções gratuitas quando
disponíveis.

Nunca depender de um único provedor.

Criar:

AI_PROVIDER=gemini

e fallback:

AI_FALLBACK_PROVIDER=groq

Outro fallback possível: OpenRouter.

Os limites gratuitos dos provedores podem mudar, então o sistema deve
permitir troca de provedor sem alterar o frontend.

Criar controle de: - uso - erros - tempo - custo - limite - modelo
utilizado

------------------------------------------------------------------------

# 31. VALIDAÇÃO DA IA

A IA não pode enviar qualquer resposta diretamente para o usuário em
funcionalidades críticas.

Para questões:

IA → JSON estruturado → Zod → validação → regras de conteúdo → salvar →
disponibilizar

Para redação: IA → estrutura de correção → validação →
cálculo/normalização → resultado

Para mapa mental: IA → JSON de nós → validação → renderização

------------------------------------------------------------------------

# 32. SEGURANÇA DA IA

Proteger contra: - prompt injection - conteúdo malicioso - respostas
gigantes - loops - abuso de geração - spam - tentativas de consumir a
API

Implementar: - rate limit - limites de tamanho - timeout - logs -
validação - cache quando possível

Nunca colocar API key no frontend.

O AGENTS.md deve instruir o Codex:

1.  Leia a arquitetura antes de alterar código.
2.  Não reescreva componentes existentes sem necessidade.
3.  Não crie dependências desnecessárias.
4.  Use TypeScript estrito.
5.  Use componentes reutilizáveis.
6.  Não colocar segredo/API key no frontend.
7.  Toda operação sensível deve passar pelo servidor.
8.  Respeitar RLS do Supabase.
9.  Validar entradas com Zod.
10. Criar testes para lógica importante.
11. Rodar lint após mudanças.
12. Rodar testes relevantes.
13. Não quebrar funcionalidades existentes.
14. Não inventar tabelas do banco.
15. Alterações de banco devem ser migrations.
16. Não modificar design system sem motivo.
17. Usar os tokens de design existentes.
18. Preferir SVG.
19. Respeitar acessibilidade.
20. Respeitar prefers-reduced-motion.
21. Não usar cores fora do design system sem justificativa.
22. Não colocar monetização fora da loja de avatar.
23. Não vender conteúdo educacional.
24. Não chamar APIs de IA diretamente pelo browser.
25. Não apresentar conteúdo gerado como oficial.
26. Antes de terminar uma tarefa, verificar build/lint/testes.

# 44. ACESSIBILIDADE

Implementar: - teclado - foco visível - labels - aria quando
necessário - contraste - navegação sem mouse - reduced motion - textos
alternativos

Nunca usar cor como único indicador.

Exemplo: não mostrar apenas vermelho para "erro". Usar também ícone e
texto.

------------------------------------------------------------------------

# 45. PERFORMANCE

Priorizar: - Server Components quando apropriado - carregamento sob
demanda - imagens otimizadas - SVG leve - lazy loading - cache - queries
específicas - paginação - evitar renders desnecessários

Não buscar todos os dados do usuário na Home.

------------------------------------------------------------------------

# 46. SEGURANÇA

Obrigatório: - secrets somente no servidor - RLS - validação de
entrada - rate limit - proteção de rotas - controle de permissões -
logs - proteção de webhook - sanitização de conteúdo - limites de upload

Criar roles: - student - admin

No futuro: - moderator - content_editor

------------------------------------------------------------------------

# 47. LGPD

Como o produto será voltado para estudantes brasileiros, o projeto deve
ser pensado desde o começo para privacidade.

Implementar: - política de privacidade - termos - controle de conta -
exclusão de conta - minimização de dados - proteção de dados - controle
de consentimento quando necessário

Se houver usuários menores de idade, avaliar os fluxos de consentimento
e responsabilidades aplicáveis antes do lançamento comercial.

------------------------------------------------------------------------

# 48. ANALYTICS

Métricas do produto:

-   usuários cadastrados
-   usuários ativos
-   sessões
-   questões respondidas
-   taxa de acerto
-   redações
-   mapas
-   simulados
-   sequência média
-   retenção
-   uso da IA
-   erros da IA
-   itens de avatar mais equipados
-   conversão da loja

Não coletar dados desnecessários.

------------------------------------------------------------------------

# 49. EXPERIÊNCIA DO ESTUDANTE

O NEXO deve sempre responder:

1.  O que devo estudar?
2.  Por que preciso estudar isso?
3.  O que devo fazer agora?

Exemplo:

"Você está com dificuldade em Probabilidade."

"Por isso, o NEXO recomenda revisar este conteúdo."

"Depois faça estas 5 questões."

"Se atingir 80%, avance para o próximo nível."

------------------------------------------------------------------------

# 50. ESTILO DOS TEXTOS DA INTERFACE

Tom: - amigável - motivador - direto - jovem - profissional

Evitar: - infantilização - excesso de emojis - linguagem forçada -
frases genéricas

Exemplo:

Ruim: "Uau!!! Você é incrível!!! Continue assim!!! 🔥🔥🔥"

Bom: "Boa evolução. Você melhorou 12% em Matemática esta semana."

------------------------------------------------------------------------

# 51. O QUE NÃO FAZER

Não criar: - assinatura obrigatória - conteúdo bloqueado por pagamento -
energia limitada para estudar - vidas para questões - loot box -
cassino - roleta de pagamento - vantagem acadêmica paga - anúncio
durante redação - anúncio no meio da questão

Não transformar educação em pay-to-win.

------------------------------------------------------------------------

MVP:

3.  Matérias

7.  Conteúdo

------------------------------------------------------------------------

# 53. DEFINIÇÃO DE PRONTO

Uma funcionalidade só está pronta quando:

-   funciona
-   está integrada
-   tem estados de loading
-   tem estado vazio
-   tem tratamento de erro
-   é responsiva
-   é acessível
-   possui validação
-   não expõe secrets
-   possui testes quando aplicável
-   passa lint
-   passa typecheck
-   não quebra outras telas

------------------------------------------------------------------------

# 54. PRINCÍPIO FINAL

O NEXO deve ser construído como um produto real.

A IA não é o produto.

A IA é uma camada do produto.

O produto é:

ESTUDANTE ↓ DIAGNÓSTICO ↓ PLANO ↓ CONTEÚDO ↓ QUESTÕES ↓ ERROS ↓ REVISÃO
↓ REAVALIAÇÃO ↓ EVOLUÇÃO ↓ GAMIFICAÇÃO ↓ RETORNO AO ESTUDO

A plataforma deve aprender com o comportamento do estudante e melhorar a
recomendação ao longo do tempo.

------------------------------------------------------------------------

# 55. PRIMEIRA TAREFA DO CODEX

O primeiro prompt recomendado para o Codex:

"Leia o arquivo de especificação do NEXO e o AGENTS.md. Não implemente
funcionalidades ainda.

Primeiro: 1. inicialize o projeto Next.js com TypeScript e App Router;
2. configure Tailwind CSS e shadcn/ui; 3. configure ESLint e formatação;
4. crie a estrutura de pastas definida; 5. crie o design system inicial
com os tokens do NEXO; 6. configure o Supabase sem criar lógica de
negócio; 7. crie o layout base responsivo; 8. crie componentes UI
reutilizáveis; 9. crie README.md explicando como executar o projeto; 10.
crie .env.example sem nenhuma chave real; 11. rode lint, typecheck e
build.

Não implemente IA, pagamentos, loja ou banco de negócio nesta etapa.

Ao terminar, mostre um resumo dos arquivos criados, problemas
encontrados e comandos executados."

Não implemente IA, questões ou loja ainda.

Crie migrations necessárias, RLS e testes. Rode lint, typecheck e
build."
